# Agent Notes

Notes 保存重要需求、设计和架构取舍的依据与结论：解决什么问题、为什么采用这个方案、考虑过哪些替代方案，以及接受哪些代价。

## 与其他文档的边界

[架构文档](../architecture.md) 维护当前职责、消息流和行为契约；Note 记录选择方案的理由、替代方案和代价。Note 的 `Decision` 保留解释取舍所需的决定摘要，并链接当前契约，不复制完整的接口、配置清单或实现说明。

代码与测试承载具体实现和行为验证；Note 可以引用支撑决定的验证证据与已知缺口，不复述代码或测试步骤。

## 何时记录

只记录有长期影响、代码、测试与现有文档不能充分解释的取舍，例如会话隔离、消息投递语义或 dsh 接入方式。

已经落地的决定直接记录为 `implemented`，无需先创建 `proposed` 或补走状态流转；尚需权衡或尚未完整落地的重要方案可以记录为 `proposed`。

普通想法、待办、小调整和项目初始化整理留在当前讨论或待办中，无需逐项创建 Note。写之前先检索已有记录，避免重复记录同一决定。

## 路径与分类

沿用 dsh 的路径形式 `{lifecycle}/{class}/YYYY-MM-DD-topic-title.md`，日期为主题首次提出的日期。目录随实际记录创建，使用相对 Markdown 链接引用相关记录。

| 分类 | 负责内容 |
|---|---|
| `feature` | 新增面向用户或模型的能力 |
| `bug-fix` | 修复缺陷或补齐行为缺口的重要取舍 |
| `simplification` | 移除代码、行为或接口且不新增能力 |
| `architecture` | 运行时结构、模块关系与职责边界 |
| `process` | 围绕代码的开发工具、策略与工作流程 |
| `testing` | 测试设施与测试策略 |

## 状态与模板

| 生命周期 | 含义 |
|---|---|
| `proposed` | 尚未落地或只部分落地的方案 |
| `implemented` | 已落地的决定；被取代时在正文标明适用范围与后继记录 |
| `rejected` | 被否决的方案，状态行写明一行否决理由 |

文件的 `Status:` 与所在生命周期目录一致。新建记录复制 [对应模板](TEMPLATE.md)，填写实际内容。

## 维护

- 已有提案落地时更新路径、状态和正文，将 `Proposal` 改为描述实际决定的 `Decision`，验收条件与风险改写为实际后果或验证结果。
- 否决时保留当时的方案正文，在状态行说明理由，并移动到对应生命周期目录。
- 决定不变时，在同次变更中更新路径、名称及实现方式等事实；改变所记录的决定或取舍理由时另建 Note，保留旧记录的决定与依据。
- 新决定落地并取代旧决定时，新旧记录双向链接。旧记录保留 `implemented`，在 `## Problem` 的首段说明被取代的范围、后继 Note 和当前契约入口；部分取代时同时写明仍适用的范围。被取代部分保留原决定与理由，并明确其历史适用范围；仍适用部分继续同步当前事实。
- 移动或删除记录时修复所有入站链接，报告实际完成的验证与已知限制。记录难以检索或维护时再引入专门的索引、合并或归档流程。
